# 风格与写页规则：为什么这么定

`SKILL.md` 里只写了「做什么」。这里写每条规则从哪来、好坏例子对照，拿不准的时候翻这里。
这些规则来自作者在几十期技术讲解 deck 上被读者反复纠正的记录——同一个问题被指出两次以上，才进这份清单。

## 一、视觉：为什么是暖纸底 + 赭橙

默认视觉是在几套风格（上游的苹果浅灰风、几种 HTML 设计风格）之间**盲测**选出来的：同一份内容做成几版，
去掉来源标记让读者打分，暖纸底这一版得分最高。读者给的理由和不满，直接变成了下面几条：

| 读者原话的意思 | 落到模板里 |
| --- | --- |
| 图形化表达好、视觉元素丰富，「读图比读数字友好太多」 | 图示五色语义，模块一眼分得开；比例画成长度（`.bars`） |
| 很反感「一张图里几个方块，每个方块一个数字」的汇总页 | 模板去掉了数字卡页型，换成长度条页 |
| 另一份同风格 deck「字稍小了一些」 | 字号整体大一档：讲稿 26px、图内 ≥ 22px，任何文字 ≥ 22px |
| 颜色要丰富、饱和度够，不同模块差异一眼看出 | 五色底色选的是中等饱和度，彼此色相拉开 |

具体 token：

```
底    --bg     #F3EFE6   暖纸色，比纯白柔和，投影仪和屏幕上都不刺眼
网格           120px，线色 #1C1B19 的 8% 透明度——只在留白处隐约可见，给页面「工程图纸」的秩序感
墨    --ink    #1C1B19   不用纯黑
次要  --muted  #6E685E   暖灰，和底色同一色温
强调  --accent #C2410C   赭橙：在暖底上足够跳，又不像纯红那样像报错
第二  --accent2 #3E5C76  灰蓝，只给「对照路线」用
kicker         等宽字 + 强调色：像图纸角标，一眼分清「出处 / 口径」和「标题」
```

**强调色一页只点一处。** 标题里点了一个词，图里就别再出现第二个强调色块；读者的眼睛只该被拉去一个地方。

五色语义沿用论文架构图的惯例（灰 = 输入输出，蓝 = Norm / 注入，紫 = 条件 / 调制，橙 = 注意力等核心机制，
绿 = FFN），读过论文图的人不用看图例也大致猜得对。关键是**全篇一致**：第 3 页的浅蓝是编码器，
第 20 页的浅蓝就不能变成「奖励」。

## 二、标题先说目的，再说做法

**问题**：标题直接甩出操作（「2×2 合并成 4096 维」）或效果（「token 减少 75%」），读者的第一反应是
「我为什么要做这个？」——前因没交代，后面的机制再清楚也接不上。

**写法**：每页（以及每一段）按这个顺序：

```
目的   这一步要达到什么            → 把视觉 token 送进语言模型
限制   卡在哪                      → ① token 太多，注意力成本随数量平方涨
                                     ② 维度和特征空间都和语言模型不一样
做法   所以怎么做                  → 2×2 合并减数量；MLP 换到语言模型的空间
效果   换来什么                    → token 少 4 倍，注意力计算量少 16 倍
```

标题放「目的 + 做法」（或问句形式的目的），限制和效果放 sub、talk 或图上：

| 不好 | 好 |
| --- | --- |
| 2×2 合并 + MLP 投影 | 要把图送进语言模型：先减数量，再换空间 |
| token 减少 75% | 为了让注意力算得起：token 少 4 倍，计算量少 16 倍 |
| 方法概述 | 为什么不直接把像素喂给语言模型 |

段与段之间用「但是……所以……」接：上一段的做法留下了什么新问题，正好是下一段的目的。

## 三、结论先行

标题、sub、talk 的第一句都是结论。栏目名（「实验结果」「消融」「方法」）没有信息量，
读者翻完 30 页只记得标题——标题就该是这页要他记住的那句话。

| 不好 | 好 |
| --- | --- |
| 实验结果 | 客服持平，发票输 13 个点 |
| 校准实验 | 两端可信，中间不可信 |

## 四、图先全出，再逐项高亮

**问题**：分步页里元素一批一批冒出来，或者说明文字先于图出现（「两根条一样长」出现时条还没画），
读者会困惑「什么两根条」。

**写法**：图一出现就是完整的（未高亮状态），之后讲到哪一项就高亮哪一项。模板的分步高亮页已经按这个实现：
第 0 步是全图，`J` 只移动高亮。讲具体论文时，放论文原图而不是自己重画的简化版——图文要一致。

## 五、页上不写自我批判和免责声明

**问题**：「这个数字可能偏低」「早期版本这里写错了」「这套划分有盲区」——写进页面的每一句，
都应该是能直接拿去讲的。修正史和对自己方法的反省，是写给作者自己的，不是给读者的。

**原则**：一个数字自己都不信，正确做法是**不写它**，而不是写上去再附一段免责声明。

界线：

- **保留**——口径说明：分母是什么、按什么算、示意还是实测、数据源的固有限制。读者需要它判断结论的适用范围。
  放 kicker（`· 按公式算，不是实测`）。
- **移走**——修正史、踩坑、对结论的对冲。进项目的工作日志，不上页。

## 六、数字画成图

读数字费劲，读图形轻松。「1024 → 256」写成两个数字，读者要心算；画成两根条，一眼看出短了四分之三。

- 比例、倍数、前后对比 → 长度条（`.bars`），条长按真实比例写，不为好看改。
- 数量 → 格子（几个 token 就画几个小方块，太多就画一行示意 + 标总数）。
- 过程 → 中间状态（每一步之后张量长什么样，形状就近标）。
- 几个方案在几个维度上的精确对照 → 才用表。

## 七、当页定义，读者零上下文

deck 是发出去让人自己读的。读者没参加你们的讨论，不知道内部代号，也不会回翻 20 页找某个缩写的定义。

- 每个符号、缩写、指标、组件名，在**出现的那一页**给一句话定义或公式。
- 公式每个符号用大白话说一遍：`N = (H/P) × (W/P)`，N 是 token 数，H、W 是图的高宽，P 是切块边长。
- 抽象概念先给直觉（示意图、几何图、伪代码），再给公式。
- 自己的归纳要说是归纳（「我读出来的」），不包装成论文结论。

## 八、多用真实素材，一个方法不止一张架构图

**问题**：全篇方块箭头和表格，「一张论文原图都没有，流程图以外的示意图一张都没有」。

- 论文原图、真实输入输出、真实例子优先。截图标明模型名和图号。
- 讲一个方法，至少回答：输入怎么进、怎么训、怎么推、数据怎么造，各配一张示意，再附效果。
- 流程图从**真实的原始输入**画起（一张真实图片、一句真实指令），每个中间量标它从哪来、怎么算。
- 不批量套「一页三张横卡」——那是在用版式掩盖内容不够具体。

## 九、读者追问 = 页面没讲清

读者问「这页的 X 是什么意思」，问题本身就说明页面没讲清楚。回答完直接把改进落到页上
（补 sub、改标题、加一句 talk），重新截图自查，再一两句话说改了哪页。不要以「要不要我改？」结尾——
那是多一轮来回。

点出一种改法并说「同类页都改」时，把所有同类页一起改掉，不要只改被点名的那一页。
