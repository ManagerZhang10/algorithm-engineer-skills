# 工作汇报写作（Working Report）

把零散项目材料组织成一场听众能复述主线、讲述者能说明判断与成长的工作汇报。优先帮助讲述者形成自己的故事，不把素材、截图或参考帖直接拼接成逐字稿。

## 先确定任务形态

- 用户提供项目材料时，先用五层框架判断材料目前停在哪一层，再设计升级方式。
- 用户要求完整汇报骨架、45 分钟时间分配或可直接填写的 Markdown 时，读取 [45 分钟工作汇报模板](references/45-minute-work-report-template.md)。
- 用户需要判断每层的含义、证据标准或如何从低层升级时，读取 [五层汇报框架](references/five-level-reporting.md)。

## 用五层框架升级汇报

先保留材料中已证实的事实，再向上组织叙事；不要为了显得“层级高”而虚构全局判断或业务价值。

1. 给每个项目标记它当前最充分支持的层级，以及证据、缺口和下一步。
2. 层级 1 是基础：讲清问题、行动和结果；没有这一层的事实，不能跳到抽象愿景。
3. 层级 2–4 分别增加可复用方法、全局判断和明确角色；应由真实项目过程和证据支撑。
4. 层级 5 是提出经验证或明确待验证的增量价值，不等同于夸大已有影响。
5. 最终汇报要呈现一条贯穿项目的故事：共同目标 → 关键能力建设 → 证据与局限 → 个人角色与下一步。

## 汇报写作与视觉表达

- 先写项目之间的关系和每个项目的一句话结论，再填背景、方案、难点与指标。
- 每个项目沿用同一结构：一句话结论、问题与目标、方案全景图、难点与应对、收益与产出、下一步。
- 文字用于结论、证据和讲述提示，不写成逐字稿；首次出现的技术缩写应给出全称与用途。
- 优先使用方案图、前后对比、具体 case 和 demo 替代长段文字。AI 生成的流程图或结构图应由人核对逻辑、文字、脱敏和版式后再使用。
- 数字附近说明比较对象、样本范围或验证状态；区分已验证事实、个人判断和待验证假设。

## 交付前检查

- 讲述者能否脱离文档，在一分钟内说出共同主线和三个项目的关系？
- 每个项目是否都能回答“问题是什么、我做了什么、为什么这样做、结果如何、下一步是什么”？
- 是否删除或泛化真实姓名、内部项目/系统名、内部链接、凭据、未公开数据，以及可反推出敏感业务的信息组合？
- 是否已按实际可讲述时长预演，并优先删去背景与重复内容而不是删方案和证据？
